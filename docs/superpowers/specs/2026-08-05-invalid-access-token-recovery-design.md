# 失效 Access Token 重补设计

## 背景与目标

现有实现把“补 AT”限定为 `access_token` 为空，这与真实需求相反。实际账号均已保存 AT，需要处理的是 AT 已失效后，通过 ChatGPT 网页登录和原邮箱 OTP 获取新 AT，并在成功后替换旧 AT。

本次修正保留已有登录、队列、停止、日志和写回能力，重新定义任务资格、替换规则和 WebUI 入口。

## 方案选择

考虑过三种方案：

1. 只允许套餐检测返回 HTTP 401 的账号重补。误操作少，但套餐状态可能尚未查询或已经过期。
2. 只允许用户手动强制重补任意账号。实现直接，但失效账号无法自动筛选。
3. 同时支持 HTTP 401 自动识别和手动强制重补。既能批量处理已确认失效账号，也能覆盖尚未检测或状态异常的账号。

采用方案 3。

## 资格判断

账号满足以下任一条件即可进入重补队列：

- 自动模式：账号已有 `access_token`，且最近一次套餐检测明确返回 HTTP 401。
- 手动强制模式：用户对任意已有 `access_token` 的账号点击“重补AT”，或勾选后批量强制重补。
- 兼容模式：账号确实缺少 `access_token` 时，仍允许沿用现有补全流程，但不再作为主要入口和主要验收目标。

`queued` 或 `running` 状态继续视为忙碌，同一账号同一时间只允许一个任务。

## 数据与替换规则

任务开始前读取并保留旧 AT，不提前清空账号记录，也不提前修改 Token 导出文件。

网页版登录取得 session 后必须满足：

- session 包含非空 `accessToken`；
- 对已有 AT 的账号，新 AT 必须与旧 AT 不同；
- 用户、设备、代理等返回数据通过现有字段校验。

只有全部校验通过后，数据库层才在同一锁范围内原子替换 AT、更新账号元数据和恢复状态，并同步：

- `注册成功的邮箱.json`
- `注册成功的邮箱.txt`
- `注册成功的token.txt`
- `accounts_viewer.html`

任务失败、停止、登录超时、账号停用、手机号验证、OTP 失败、session 缺少 AT 或返回相同 AT 时，旧 AT 和原账号元数据保持不变，只更新任务状态、错误和日志。

## 服务与 API

现有恢复服务增加 `force` 参数并贯穿单个、批量、数据库领取和任务日志：

- `force=false`：仅接受 HTTP 401 或缺少 AT 的账号。
- `force=true`：接受任意已有 AT 或缺少 AT 的账号。

单个 API 请求体支持：

```json
{"account_id": 168, "force": true}
```

批量 API 请求体支持：

```json
{"account_ids": [168, 167], "force": true}
```

普通响应和日志不包含完整旧 AT 或新 AT。日志只记录账号 ID、触发方式、是否强制、状态和脱敏错误。

## WebUI

账号页调整如下：

- 已有 AT 且套餐检测为 HTTP 401：Token/套餐区域标记“AT失效”，行操作显示醒目的“重补AT”。
- 已有 AT 但未标记失效：行操作仍提供“重补AT”，点击后明确提示这是强制重新登录并替换 AT。
- 缺少 AT：保留“补AT”。
- 批量按钮由“补缺失AT”改为“重补AT”，对选中账号发送 `force=true`。
- 确认框显示总数、HTTP 401 数量、普通强制重补数量和正在运行的跳过数量。
- 运行、停止、失败、日志查看和轮询继续沿用现有交互。

## 错误处理

- HTTP 401 只作为失效资格信号，不直接清空 AT。
- 新 AT 与旧 AT 相同时任务标记失败，错误为“登录未返回新的 Access Token”。
- 成功写回前出现任何异常都保留旧 AT。
- 成功写回后若派生文件同步失败，沿用数据库层原子写文件和回滚策略，避免 JSON 与 Token TXT 不一致。
- 错误信息继续清洗 JWT、代理凭据、邮箱取件凭据和认证 URL。

## 测试与验收

自动化测试至少覆盖：

- HTTP 401 且已有 AT 的账号可领取任务。
- 非 HTTP 401 且已有 AT 的账号在 `force=false` 时跳过，在 `force=true` 时可领取。
- 缺少 AT 的兼容流程仍可领取。
- 成功获得不同的新 AT 后替换旧 AT并同步导出。
- 新 AT 与旧 AT 相同时失败并保留旧 AT。
- 登录、OTP、停止、账号停用等失败均保留旧 AT。
- 单个和批量 API 正确传递 `force`。
- WebUI 对 HTTP 401 账号显示“AT失效/重补AT”，批量按钮发送强制模式。
- 日志和 API 不泄露旧 AT 或新 AT。

人工验收使用当前数据中最新注册且套餐检测为 HTTP 401 的账号，优先账号 ID `168`（创建时间 `2026-08-04T23:07:19`）。验收前保留其旧 AT，直接点击“重补AT”；成功时确认 AT 已变更，失败时确认旧 AT 仍在。

## 验收标准

- 已有但失效的 AT 可以单个或批量重补。
- 任意已有 AT 的账号可以通过明确确认后强制重补。
- 成功后才替换旧 AT；失败和停止始终保留旧 AT。
- HTTP 401 账号在页面上有清晰失效标记和操作入口。
- 缺失 AT 的原兼容能力不回退。
- 全量自动化测试通过，真实验收使用最新 HTTP 401 账号。
